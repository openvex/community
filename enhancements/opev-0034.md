# OPEV-0034: Formal Identity Struct

OpenVEX names the actors involved in a document with free form strings. The
document `author`, the statement `supplier` and the document `tooling` fields
take a string that the specification does not structure. The field holds
anything from a person's name to an email address to a URL, and consumers
cannot tell which, nor tie it to anything outside the document.

The [v1 roadmap] lists a formal identity struct as a requirement: the string
field "has proven to be unsuitable for more advanced operations and proposed
features such as multi-stakeholder approval of statements or inclusion
records". An author that cannot be matched to the identity that signed the
document, to a Sigstore certificate or to an organization record cannot take
part in any of those.

This OPEV proposes an `identity` data structure for OpenVEX v1 and makes the
fields that name actors accept it, while keeping the string form they take
today.

### How it works

An identity names a person, an organization, a tool or an AI agent. It carries
an optional global `@id`, a display name, a type and a map of identifiers in
external systems, keyed by identifier type in the same style as product
identifiers:

```json
"author": {
  "@id": "mailto:security@example.com",
  "name": "Example Security Team",
  "type": "organization",
  "identifiers": {
    "email": "security@example.com",
    "oidc_issuer": "https://accounts.google.com",
    "oidc_subject": "security@example.com"
  }
}
```

The `author`, `supplier` and `tooling` fields accept either a string or an
identity struct. The string form stays an opaque label and the struct is what
tooling matches against. Because OpenVEX is JSON-LD, an identity with an `@id`
is a node in the document graph, and a struct carrying only `@id` is a
reference to an identity described elsewhere. The identity struct is also an
extension point, so extensions can attach data such as certificate details.

The full definition, including the field tables, the identifier type catalog,
the JSON-LD context and JSON schema changes and the compatibility rules, is in
the identity specification linked below. Details are discussed in that pull
request, this OPEV decides whether OpenVEX v1 adopts the structure.

### Benefits

- Actors in a document can be matched to signing identities, identity
  providers and organization records instead of being compared as strings.
- Features on the v1 roadmap that name actors, such as multi-stakeholder
  approval and inclusion records, get a single structure to build on.
- Every document valid today stays valid. The string form is retained in all
  three fields.

### Consequences

- Documents that use the identity struct require a v1 consumer. They declare
  the v1 context IRI, so older consumers can detect the newer format. go-vex
  already selects a parser from the context version.
- The JSON schema changes `author`, `supplier` and `tooling` to accept a string
  or the identity struct, and the context gains scoped definitions for the
  identity terms.
- go-vex and vexctl need to parse both forms and to emit the struct.
- The identifier type catalog will need curation as new identity systems are
  requested.
