# OPEV-0017: OpenVEX Extensions

## 🖊️ Enhancement Overview

OpenVEX implements the [Minimum Requirements for VEX] and pledges not to break
upstream VEX. That pledge has so far kept out of the format any information
beyond the VEX minimum elements, even when the community has asked for it. The
most recent example is [OPEV-0016], which proposes carrying vulnerability
severity ratings in a statement.

This OPEV proposes an official extension mechanism for OpenVEX. It gives the
project, vendors and implementers a way to enrich OpenVEX documents with
additional data while documents remain valid VEX, backwards compatible and
processable by tools that know nothing about the extension.

### How it works

OpenVEX documents are JSON-LD. An extension is a JSON-LD context, published at
an IRI the extension author controls, that binds a short prefix to the
extension's namespace. A document opts into an extension by listing that IRI in
its `@context` array, and carries the extension data in prefixed fields placed
next to the core OpenVEX fields:

```json
{
  "@context": [
    "https://openvex.dev/ns/v0.2.0",
    "https://example.com/ext/myext/v1"
  ],
  "@id": "https://openvex.dev/docs/example/vex-ext-0001",
  "author": "Example Security Team",
  "timestamp": "2026-05-07T18:02:03Z",
  "version": 1,
  "statements": [
    {
      "vulnerability": { "name": "CVE-2026-0001" },
      "products": [ { "@id": "pkg:apk/wolfi/libfoo@1.4.2-r0" } ],
      "status": "not_affected",
      "justification": "vulnerable_code_not_in_execute_path",
      "myext:ticket": "https://example.com/tickets/SEC-8812"
    }
  ]
}
```

Extension fields may appear at five extension points: the document, each
statement, the vulnerability, each product and each subcomponent. Removing
every extension field from a document leaves a valid OpenVEX document whose VEX
meaning is unchanged. Extensions are forbidden from altering the meaning of any
core field.

Parsers that implement the mechanism route extension data to handlers keyed by
the extension IRI declared in `@context`. Data for extensions a parser does not
know is preserved and passed through. Parsers that do not implement the
mechanism see ordinary unknown fields, which the specification already requires
them to tolerate.

The full design, including the rules for defining, versioning and hosting an
extension, prefix handling, processing rules for producers, consumers and
merging tools, and the changes the core specification needs, is in the
extensions specification linked below. Details are discussed in that pull
request; this OPEV decides whether OpenVEX adopts the mechanism.

### Benefits

- OpenVEX gains a sanctioned way to carry data beyond the VEX minimum elements
  without changing the core format for every new need.
- Proposals such as [OPEV-0016] can ship as extensions, be adopted by
  interested users, and graduate into the core specification once proven.
- Anyone can publish an extension under their own namespace. No registry or
  approval from the project is needed for third party extensions.
- Extended documents remain valid JSON-LD. Extension data expands to proper
  IRIs and joins the same graph as the core OpenVEX terms.

### Consequences

- The `@context` field accepts an array, and the JSON schema admits prefixed
  fields at the five extension points. Both are backwards compatible for
  readers; the schema change requires a new spec version.
- Tools that rewrite documents (for example `vexctl merge`) should preserve
  extension data they do not understand. go-vex and vexctl need a plugin
  registry and passthrough support, which this OPEV does not specify.
- The OpenVEX context and extension contexts must be served as JSON-LD at their
  IRIs for remote JSON-LD processing to work. Today the core context URL
  redirects to GitHub.
- The project will need a lightweight process for publishing official
  extensions under `openvex.dev/ext/`. That process is left to a follow-up.

## ❓ Enhancement Questions

Does this enhancement propose a change to the OpenVEX project's governance
structure?

**NO**

Does this enhancement propose a breaking change with the upstream VEX design
established by the VEX Working Group?

**NO**. Extension data is additive. A document stripped of every extension
field is an unchanged, valid VEX document, and the mechanism forbids extensions
from altering the meaning of any core field.
