# OPEV-0035: Dependency Path for Subcomponents

## 🖊️ Enhancement Overview

A VEX statement names a product, a vulnerability and the subcomponent the
vulnerability lives in. When a product includes the same subcomponent more
than once, through different dependencies, OpenVEX cannot tell the inclusions
apart. One route may expose the vulnerable code while another does not, and
today a statement can only speak about the subcomponent as a whole. The
[v1 roadmap] lists this under "Vulnerability Import Path".

This OPEV proposes a `dependency_path` field on subcomponents: an ordered list
of components describing the chain of dependencies through which the
subcomponent reaches the product. A statement with a path applies only to
inclusions that follow that chain.

### How it works

The path is read from the product down. Its first element is a direct
dependency of the product and each following element a dependency of the one
before. The path may stop at any depth, so an author can state exactly as
much as they know, or run all the way down to the subcomponent itself:

```json
{
  "identifiers": {
    "purl": "pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1"
  },
  "dependency_path": [
    {
      "identifiers": {
        "purl": "pkg:maven/org.springframework.boot/spring-boot-starter-logging@2.6.1"
      }
    }
  ]
}
```

This says: the vulnerability in log4j-core does not affect me when log4j-core
arrives through the Spring Boot logging starter. It says nothing about other
routes, which the author can cover with further statements.

A consumer applies a path-scoped statement to an occurrence of the subcomponent
only when the chain it observed starts with the stated path. Where it comes
from is up to the consumer: SBOM dependency graphs, lockfiles, or reachability
tools that report the chain through which vulnerable code is reached. A
consumer that cannot determine the chain does not apply the statement and
reports it as present but not evaluated. A path-scoped statement therefore
never silences a finding on a consumer that cannot verify it.

The full definition, including the component type split, the matching and
finding resolution rules, the JSON-LD context and JSON schema changes, is in
the dependency path specification in
[openvex/spec#73](https://github.com/openvex/spec/pull/73). Details are discussed
in that pull request.

### Benefits

- Authors can issue precise statements for products that include a
  subcomponent through several routes, including different statuses per route.
- The knowledge an author has, which is greatest for direct dependencies, maps
  directly onto what the field lets them state.
- The design fails closed. Consumers without chain data never over-apply a
  statement.
- Every document valid today stays valid. The field is additive.

### Consequences

- Documents that use the field require a v1 consumer and declare the v1
  context IRI.
- The JSON schema is reorganized so that `component`, `subcomponent` and
  `product` are three named types, aligning the schema with the specification
  prose. Documents are unaffected.
- go-vex and vexctl need to accept observed chains as a matching input and to
  report the "present but not evaluated" outcome distinctly. vexctl cannot
  evaluate paths from inventory-only scanner output.
- Findings without a chain resolve only when every chain to the component is
  covered by a statement, which is the correct but stricter behavior.
